## 6. Decisions not in the spec

1. **The body line of the OLLAMA ERROR block is `error.detail`.** FR-202 says it is taken from `failure.body`, but the engine result carries only `detail` (Ollama's JSON `error` string, else the exception type and `webStatus`), not the body. For an HTTP error with a JSON body the line is the same text as before; for a body without an `error` member it is the type name instead of the raw body. Printing the raw body would need a field in the result (engine change, out of scope).
2. **Where the added lines go.** Inside the `=== OLLAMA ERROR ===` block: `Status:` (only when there is an HTTP status), the detail, `Category:`, `Hint:`. For `empty_response` and `thinking_budget_exhausted` and for `context_budget_exceeded`: `Category:` and `Hint:` before the `ERROR:` line (no OLLAMA ERROR block, as before). For an unreachable server or a missing model: after the legacy lines and before `ERROR:`. The localized message line is dropped (OQ-214).
3. **Section lines** of a budget refusal are one per part of the builder, so the template text appears several times: `  <name> (<kind>): <chars> characters, about <tokens> tokens`, preceded by `Estimated N tokens, available M.` (nine parts without context, eleven with it).
4. **`Warning: budget_exceeded ...` is printed after the call returns**, from `meta.warnings`, because the engine, not the script, computes the budget; it is not printed before the request.
5. **`Retrying (attempt k of N) after <category>, waiting S s.`** is printed by an `-OnRetry` hook that uses only its parameters; `k` is the attempt about to be made (the engine's argument).
6. **`$execution.model` is set to the trimmed `-Model`**, because the engine and `Test-OllamaModel` read the model from the record; the legacy script trimmed it before use.
7. **A thrown message of the wrappers (wip branch):** `Ollama request failed: <category>: <detail>` (the spec says `<detail>`); an empty or `length`-empty answer returns `''` as before instead of throwing.
8. **Two assertions are added next to `think member`** (the value is true, and a JSON boolean). They are new assertions, not edits of an existing one; AC-218 row 2 names only the changed expectation.

## 7. Owner decisions

**D-A. Relocating the two wrappers cannot be done in WP-2D1 as the task and spec 4a state.** Two blockers; the full relocation is committed on `wip/phase2-wp2d1-wrappers` (`9701f3f`, `f1ad0d2`) and was not merged.

1. `review-spec.ps1` (lines 33 to 34, 112, 121) and `revise-spec.ps1` (lines 33 to 34, 148, 156) dot-source only `config.ps1` and `telemetry.ps1` and still call both wrappers. Removing them from `config.ps1` breaks both scripts, which this package must not touch. Evidence: on the wip branch `test-all.ps1` fails exactly `test-agent-telemetry.ps1` ("missing line: Review Status: PASS") and `test-registry-callsites.ps1`; everything else passes, and the new suite passes against the relocated wrappers (52 of 52 when the branch was cut; 55 of 55 after `feat/phase2-wp2d1` was merged into it, together with `test-agent-prompts.ps1`).
2. `test-agent-prompts.ps1`, "NFR-203 static scan: no HTTP route, process control, ...", forbids `Write-Host` anywhere in `agent-exec.ps1`, but FR-202 says the wrapper `Test-HarnessModelAvailable` "prints the legacy lines". AC-218 does not list this assertion for WP-2D1 (only the pinned function list). Proposed edit, applied on the wip branch: in that case, the forbidden-command check exempts `Write-Host` inside the function `Test-HarnessModelAvailable` (four lines: find the owning `FunctionDefinitionAst`, set `$deprecatedPrinter`, and test `$forbiddenCommands -contains $name -and -not $deprecatedPrinter`). The pinned function list edit (adds `Invoke-HarnessGenerate` and `Test-HarnessModelAvailable`) is on the same branch.

Proposal: do the relocation in WP-2D2, in the commit that migrates `review-spec.ps1` and `revise-spec.ps1` (they stop calling the wrappers there), and approve the scan edit; add the edit to the AC-218 table for WP-2D2. Until then both wrappers stay in `config.ps1`, behavior unchanged, and the new suite characterizes them with literal expectations, so the relocation is a tested no-op. Alternative the spec could choose: keep a copy in `config.ps1`, which duplicates the definitions.

**D-B. Spec text to correct (no requirement change):** FR-204 and M-5 say the Phase 0 and Phase 1 fake hosts "declare exactly these [five parameters] and an extra one would make every child-process suite fail". That is false: their `Invoke-RestMethod` is a simple function, which accepts and ignores undeclared parameters (section 4, M55 against `test-registry-callsites.ps1`: 55 passed, 0 failed). The engine fake host of this package enforces it; the old hosts do not. The spec sentence and the WP-2C note ("rejection by the Phase 1 hosts' own parameter lists") should say so. No assertion of the old suites was changed for it.
