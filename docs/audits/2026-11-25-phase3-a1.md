# Phase 3 package A1 - telemetry mutex, FileStream append, locked reader

## Executive summary

**Status:** implemented, tested, awaiting review. Nothing pushed or tagged.

**What changed**
- `scripts/lib/telemetry.ps1`: `Write-HarnessModelTelemetry` now takes the named mutex `Global\AiHarnessTelemetry-<first 16 hex of SHA-256 of the lower-cased long, trimmed log directory path>` around its whole file section (JSONL append, CSV header decision, CSV append). Each file is appended through one `FileStream` (`Append`, `Write`, `FileShare.ReadWrite`) in a single write, with an `IOException` retry every 25 ms. New parameter `-LockWaitMs` (default 10000), added last.
- New helpers in the same file: `Get-HarnessLongPath` (absolute, 8.3 expanded, trailing separators trimmed), `Get-HarnessTelemetryMutexName`, `Enter-HarnessTelemetryLock`, `Exit-HarnessTelemetryLock`, `Add-HarnessTelemetryText`, and the FR-307 reader `Read-HarnessModelTelemetry -Root [-FromOffset] [-LengthOnly] [-LockWaitMs]`. The reader returns `Exists, Length, Lines, LockTimedOut`; it reads inside the same lock with `FileShare.ReadWrite`, retries `IOException`, drops a leading BOM, and on lock timeout reads unlocked and sets `LockTimedOut` (the caller adds `telemetry_lock_timeout`).
- No `Local\` fallback. A refused name or a spent wait gives one `Write-Warning`, then the write goes ahead. An abandoned mutex counts as acquired; the mutex is released in `finally`.
- Bytes equal `Add-Content -Encoding UTF8`: BOM only when the file is empty or new, CRLF. The CSV missing-final-newline fix is kept; its line end now goes in front of the row in the same write. Columns, records and the CSV rule are unchanged.
- `scripts/test-agent-telemetry-v2.ps1`: 7 new cases (AC-317) and 2 edited static assertions (see Deviations).

**Files:** `scripts/lib/telemetry.ps1`, `scripts/test-agent-telemetry-v2.ps1`, this report. Nothing else.

**AC-317 evidence (suite now 43 cases, all PASS; was 36)**
- 4 child processes x 40 records: JSONL 160 parsable lines, 160 distinct `call_id`; CSV 1 header and 160 rows.
- 2 writers x 40 that read with the FR-307 reader after every write, plus a looping reader process: 80 records, 0 missing own records, 0 torn lines, no shrink.
- BOM once at creation, none later, no bare LF, bytes SHA-equal to `Add-Content`/`Set-Content -Encoding UTF8` for JSONL and CSV.
- `-LockWaitMs 300` against a holding child: exit 0, one warning, record written, waited >= 250 ms; reader reports `LockTimedOut` and still reads.
- A holder killed while holding does not block the next writer (no warning, no long wait).
- Mutex name literal check, plus trailing backslash, upper case, dot segments, forward slashes and (if the machine has one) the 8.3 alias.

**test-all (once, final):** 19 discovered, 18 executed, 18 PASS, 0 FAIL, 1 skipped (`test-spec-integration.ps1`, needs Ollama). Result PASS WITH SKIPS, equal to the baseline. No new suite file, so the count stays 19. Tripwire clean.

**Mutation proofs (temporary edit, SHA-256 of `telemetry.ps1` identical after each revert)**
1. Lock disabled (`Enter-HarnessTelemetryLock` returns at once without a mutex), 3 runs: the 4x40 case got 71, 86 and 118 JSONL lines instead of 160; the reader case saw 35 to 191 missing own records; the `-LockWaitMs` case got no warning. This is the "lock disabled loses records" evidence AC-317 asks for. Cause: .NET `FileMode.Append` seeks to the end when the file is opened, so concurrent writers overwrite each other; the mutex is what makes the append safe.
2. BOM on every append (`if ($true)` for the BOM test): 8 cases fail, including the BOM count (expected 1, got 3) and the byte-equality case.
3. Abandoned mutex counted as not acquired: **not proven**, see below.

**Deviations and doubts**
- The Phase 2 static case "telemetry.ps1 defines only Write-HarnessModelTelemetry" and the parameter count (23 to 24) had to be edited; the helper functions and `-LockWaitMs` make them necessarily false. No other Phase 2 case or golden changed. The suite header ("no child process") was edited to say the AC-317 cases start child processes. Tests use `Start-Process` only, never the lib.
- AC-317 tests live in `test-agent-telemetry-v2.ps1` (a listed file), not in a new suite, because Affected Files names no new telemetry suite.
- I read "retry until -LockWaitMs is spent" as a retry budget of `LockWaitMs` that starts at the file write, separate from the mutex wait. The spec could also mean one shared budget.
- The reader's partial last line (a writer that did not take the lock) is not trimmed; with the lock held it cannot occur.
- Abandoned-mutex rule: in this environment (Windows PowerShell 5.1) a mutex held by a killed process returned `WaitOne` true with no `AbandonedMutexException`. The `catch` is in place per spec but no test can reach it here, so the mutation proof for that rule was not possible (the mutation survived: 43/43 pass). The kill test still proves the behavior required by AC-317 (the next writer is not blocked).
- Not verified: a `Global\` name the process may not open (refused path); 8.3 alias spelling only if this machine creates short names (the test says so in its output when it skips that line); behavior on network paths.
- The unlocked fallback (timeout or refused name) can still lose records, because of the overwrite behavior of `FileMode.Append` shown in proof 1. The spec accepts this ("writes anyway relying on the retry"); it is a risk worth a review decision.

## Details

- Mutex key: `Get-HarnessLongPath` walks each component with `Directory.GetFileSystemEntries(parent, name)`, which returns the long name for an 8.3 alias; no P/Invoke, no `Add-Type`.
- Reader offsets: `FromOffset` larger than the file length is clamped to the length (nothing returned). A leading BOM is dropped only when the read starts at byte 0.
