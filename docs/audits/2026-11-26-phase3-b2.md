## 2. Interface for B4 (and B5, B8)

Dot-source `scripts\lib\workflow.ps1`. Results never travel in the pipeline. Anything a stage writes to the success stream passes through to the caller's output, so a caller that must keep stdout clean redirects it itself. Do not capture it to get results.

`Invoke-SpecifyWorkflow` parameters:

- Required: `-RunnerScript -ValidatorScript -ReviewerScript -ReviserScript -Mode -Task -Name -OutputDirectory -Result <hashtable>`.
- Optional: `-Model`, `-Profile`, `-ContextFile` (each passed to runner, reviewer and reviser only when bound) and `-Hook <scriptblock>`.

Before it calls any stage, the library refuses these as `invalid_arguments`, with legacy and CLI exit 2:

- `-Model` with `-Profile`;
- a mode other than the three (case-insensitive, like the `ValidateSet` of `specify.ps1`);
- a name outside the legacy grammar.

It never calls `exit`. It prints the legacy console lines (`Write-Host`).

`-Result` (every key is always set):

| Key | Values |
|---|---|
| `outcome` | `passed`, `failed`, `needs_input` |
| `category` | `$null` on success; `invalid_arguments`, `needs_human_input`, `validation_failed`, `stage_failed`, `max_revisions_reached`, `internal_error` |
| `stage` | id of the deciding stage, or `$null` (refused before any stage) |
| `legacyExitCode`, `cliExitCode` | per the FR-308 outcome table (below) |
| `message` | fixed wording for the CLI `ERROR:` line, `$null` on success; contains no task text |
| `error` | the `ErrorRecord` of a throw (stage, hook or workflow), else `$null`. The legacy front end does `throw $Result.error` when it is set |
| `errorSource` | `stage`, `hook`, `workflow` or `$null` |
| `specFile`, `reviewFile` | last spec and review path worked on (may not exist after a failure) |
| `revisions` | revisions started, 0 to 3 |

Outcome table as implemented. "No code" means a stage that sets no exit code. "Throws" means a stage that throws; the `ErrorRecord` is in `error`.

| Stage | Situation | legacy | cli | category | stage status |
|---|---|---|---|---|---|
| spec-generate, spec-revise | throws | 2 | 2 | stage_failed | failed, exitCode null |
| spec-generate, spec-revise | exit not 0 (no code counts as 0) | 2 | 2 | stage_failed | failed |
| spec-generate, spec-revise | ends well, output missing or empty | 2 | 2 | stage_failed | failed |
| spec-validate | exit 3 | 3 | 3 | needs_human_input | failed |
| spec-validate | exit 1 | 2 | 1 | validation_failed | failed |
| spec-validate | other code, or throws | 2 | 2 | stage_failed | failed |
| revised-validate | exit 1 or 3 | 2 | 1 | validation_failed | failed |
| revised-validate | other code, or throws | 2 | 2 | stage_failed | failed |
| spec-review | exit 0 and review present | 0 | 0 | null (outcome passed) | succeeded, verdict PASS |
| spec-review | exit 1, revision below 3 | next round | | | succeeded, verdict FAIL |
| spec-review | exit 1 at revision 3 | 1 | 1 | max_revisions_reached | succeeded, verdict FAIL |
| spec-review | exit 2 | 2 | 2 | stage_failed | failed |
| spec-review | no code, exit outside 0 to 2, or throws | 2 | 2 | stage_failed | failed |
| spec-review | exit 0 or 1, review missing or empty | 2 | 2 | stage_failed | failed |
| any | hook throws | 2 | 2 | internal_error (errorSource hook) | the workflow stops |
| none | missing stage script, or another throw outside a stage | 2 | 2 | internal_error (errorSource workflow) | |

FR-308 says "from the record, else stage_failed" for a runner, reviser or reviewer failure. The library always returns `stage_failed`. B4 replaces the category with the one in the stage's telemetry record (FR-307) when there is one.

Hook. `& $Hook -EventName <name> -Data <hashtable>`. Its output is discarded.

- `stage_begin`: `id`, `kind` (`agent` or `deterministic`), `agent` (`spec`, `spec-reviewer`, `spec-reviser` or `$null`), `attempt`.
- `stage_end`: `id`, `status` (`succeeded` or `failed`), `exitCode`, `outputPath` (the stage's expected output, or `$null` for a validator), `verdict` (`PASS`, `FAIL` or `$null`), `reason` (the fixed message on failure, else `$null`).
- `exitCode` is the raw `$global:LASTEXITCODE`: `$null` for a stage that set no code, even when it succeeded, and always `$null` after a throw. `status` says whether the stage succeeded.
- Ids and attempts follow FR-305: `spec-generate` 1, `spec-validate` 1, `spec-review` round k, `spec-revise` and `revised-validate` revision k.
- Stage warnings are not part of the contract (FR-303 lists none). B4 takes them from the telemetry record of the call (FR-307).
- A hook that throws stops the workflow with `internal_error`. B4 then finalizes the manifest itself.

Stage helpers, for `review`, `revise` (B5) and `scan`, `context` (B8):

- `Invoke-HarnessStage -Id -Kind [-Agent] [-Attempt] -Script -Arguments <hashtable> [-Hook] -State <hashtable>`. Sends `stage_begin`, resets the exit code, calls the stage and catches a throw. It fills `State.threw`, `stageError`, `exitCode` (raw), `hookFailed`, `hookError` and `hookEvent`. The caller decides the status.
- `Complete-HarnessStage -State -Status [-OutputPath] [-Verdict] [-Reason] [-Hook]` sends `stage_end`.
- `Get-HarnessStageExitCode <code> [-NullIsUnexpected]` applies the RN-8 rule.
- `Test-HarnessStageOutput <path>` returns true for an existing file that is not empty.
- `Invoke-HarnessFileStage -Id -Script -Arguments -OutputPath [-Hook] -State` is for stages without exit codes. It sets `status`, `category` (`stage_failed`) and `message`, and its `exitCode` is always `$null`.

## 3. Decisions where the spec is open, and things to note

1. **RN-8 and the reset against legacy** (summary): a deliberate divergence, reachable only with stage scripts that set no exit code. The new suite pins the new behavior: the RN-8 cases and the reviewer case through `specify.ps1`.
2. **Messages.** `stage_failed` wording:
   - "Stage '<id>' failed with exit code <n|null>."
   - "Stage '<id>' failed: it threw an exception (exit code null)."
   - "Stage '<id>' failed: exit code <n>, output file missing or empty."
   
   Other messages:
   - `validation_failed`: "Stage '<id>' failed structural validation (exit code <n>)."
   - `needs_human_input`: "Stage 'spec-validate' needs human input (exit code 3): see Open Questions in the specification."
   - `internal_error` from a hook: "The stage hook failed at <event> of stage '<id>'."
   
   None of them includes task text (NFR-305). B4 may reword them; no test outside this suite pins them.
3. **Validator exit 3** is a `failed` stage with run outcome `needs_input`. A FAIL review is a `succeeded` stage with verdict `FAIL` (FR-305), including the last one at max revisions.
4. **Wildcard paths.** Legacy used `Test-Path`, `Remove-Item` and `Get-Item` without `-LiteralPath`. I kept that unchanged so legacy behavior is exact. A path containing `[`, `]`, `*` or `?` (harness root or B4 target) breaks the workflow in the old and the new code alike. This is a follow-up for B4 when it passes target paths (FR-319 path safety).
5. **Line breaks.**
   - Redirected `Write-Host` lines end in LF and success-stream lines in CRLF. The fixtures were recorded with CRLF everywhere, and the suite compares in that form because `core.autocrlf` rewrites committed fixtures.
   - The runner's task is a here-string, so its line breaks are those of the script file, in the old code as in the new. The calls fixtures hold `\r\n` (CRLF checkout). The suite expects `\n` when `workflow.ps1` has LF line breaks. I did not run an LF checkout.
6. **AC-330 "output file missing" with the real scripts.** The real scripts always write their output unless they throw, so the case uses an expected output path different from the one passed to the script. Empty output is covered by a generated three-line script.
7. **The context pack** (`docs/phase3-context.md`) is not updated with these interfaces. As for B1, that is left to the reviewing session.
