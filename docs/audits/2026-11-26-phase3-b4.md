# Phase 3 B4: `harness specify` (run layout, manifest, checkpoints, telemetry correlation, names, overwrite, protocol)

## Executive summary

**What changed.** `Invoke-HarnessCommandSpecify` in `scripts/lib/cli.ps1` replaces the B3 stub. Before the claim it refuses `-Include` (B8), an unsafe artifact folder (FR-319 reparse checks) and an unreadable or empty `-TaskFile`; each prints one `ERROR:` line, exits 2 and creates no run. Then it claims the run and prints `RUN_ID:`. It sets `AI_HARNESS_RUN_ID` to the run id and restores the caller's value in a `finally`. It writes `inputs\task.md` and creates the manifest (`running`, stages `pending`). Before the first stage it checks `registry_invalid` (including the resolution of the three agents with `-Model`/`-Profile`), `agent_not_found`, and `artifact_exists`; with `-Overwrite` it instead moves the whole family to `runs\<id>\replaced\`. Then come the optional `load-check` stage and the B2 workflow with a hook that checkpoints the manifest atomically at every `stage_begin`/`stage_end`. The FR-308 outcome table is applied, with the category taken from the stage's telemetry record where the table says so. The final manifest is validated, then the run prints `ERROR: <category>: <text>` (nonzero exit) and `MANIFEST: <path>` last. Telemetry is joined per agent stage by byte offset plus `run_id`, through `Read-HarnessModelTelemetry` (FR-307).

**Decisions for the owner** (details in section 3):

1. The suite is named `test-harness-e2e.ps1`: "specify" is not among the Affected Files suite names.
2. `-Include` is refused before the claim with `internal_error` ("not implemented in this build"), as B3's stubs do. The reason is that the reviewer and reviser get `-ContextFile` only in B7. The scan/build-context half of AC-321 moves to B8.
3. The registry check before the first stage resolves the three agents with `-Model`/`-Profile`, so an unknown `-Profile` is `registry_invalid` before any stage.
4. The `load-check` stage has kind `deterministic`, agent null, and loads the models the run will use (with the overrides).
5. Artifact roles are `spec`, `review`, `revised-spec` (root `target`) and `replaced` (root `run`, path `replaced\<file>`); every model output and replaced file is `untrusted-draft`. `output.path` is absolute.
6. `taskSha256` is the SHA-256 of `inputs\task.md`, which is the task as UTF-8 without a BOM. A `-TaskFile` BOM is dropped. `request.taskFile` is the absolute `-TaskFile` path or null.
7. The order of checks before the first stage is registry, then agents, then family; the `-Overwrite` move happens before the load check. A failed load check therefore leaves the old family in `replaced\`, as the Edge Cases say.
8. `.gitignore` has `/runs/` (B1); AC-305 literally says `runs/`. The test accepts either.
9. AC-313 "one ERROR line": the real `run-agent.ps1` prints its own `ERROR: ...` text, so the suite counts the protocol line `ERROR: <category>:` (exactly one, just before `MANIFEST:`).
10. Concurrency (artifact lock, `concurrent_run_detected`) is not implemented here: RN-11 assigns it to B6.

**Not verified:** live Ollama; `-LoadCheck` success with the real scripts; the AC-323 name check (B9); cross-volume `-Overwrite` (copy then delete) was not exercised.

## 2. Interface for B5, B6, B7

**Reusable helpers (in `lib\cli.ps1`):**

- `Get-HarnessCliSpecDirectory -TargetPath`.
- `Test-HarnessCliArtifactDirectory -TargetPath` returns `$null` or the `invalid_arguments` text.
- `Get-HarnessCliSpecFamily -SpecDirectory -Name` returns the existing family paths.
- `Move-HarnessCliSpecFamily -Files -Destination` returns `{name, path, sha256}` per file. B5 can use it with a single file for review/revise `-Overwrite`.
- `ConvertTo-HarnessCliCategory -EngineCategory`.
- `New-HarnessCliError -Category -Message [-EngineCategory] [-HttpStatus] [-Hint]` returns the full error object; `hint` comes from the engine and `retryable` is set only for `http_5xx`/`transport_reset`.
- `Get-HarnessCliTelemetryOffset -HarnessRoot` and `Get-HarnessCliStageTelemetry -HarnessRoot -RunId -FromOffset` return `{Fields, Count, Warnings}`.

**Run state (`$Run` hashtable):**

- Keys: `Root`, `RunId`, `RunPath`, `ManifestPath`, `TargetPath`, `SpecDirectory`, `Warnings`, `Manifest`, `Stages` (`List`), `Replaced` (`List`), `Current`, `CurrentTelemetry`, `Clock`, `ExternalHook`, `ExitCode`, `Error`.
- `New-HarnessCliStage -Id -Kind [-Agent] [-Attempt]` creates a stage.
- `Invoke-HarnessCliSpecifyEvent -Run -EventName -Data` is the checkpoint hook. B5 can drive `Invoke-HarnessStage`/`Complete-HarnessStage` with it.
- `Save-HarnessCliRun -Run` and `Complete-HarnessCliSpecifyRun -Run -Status -ExitCode -RunError` finish the run: pending stages become skipped, the manifest is validated and written.
- The workflow hook reaches `$harnessSpecifyRun` (a variable of `Invoke-HarnessCommandSpecify`) through dynamic scope; a new command should declare its own variable of that name or pass `-Run` explicitly.

## 3. Decisions (detail)

See the summary list. Two more notes:

- (a) The stage `error` written at `stage_end` is provisional: the record's mapped category, or `stage_failed`. At the end, the deciding stage gets the run error.
- (b) A stage still `running` at the end (a hook failure) becomes `failed` with a fixed reason. This keeps every final manifest valid.
