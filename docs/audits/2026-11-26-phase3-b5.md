# Phase 3 B5: `harness review`, `harness revise`, `harness status`, `harness list`

## Executive summary

**What changed.** The four stubs of `scripts/lib/cli.ps1` are real commands.

- `review` and `revise` run one agent stage per run, with the B4 layout, claim, `RUN_ID:`/`ERROR:`/`MANIFEST:` protocol, `AI_HARNESS_RUN_ID` restore, manifest checkpoints, telemetry join, registry/agent checks, `artifact_exists` and `-Overwrite`.
  - `review -Revision N` reads `<Name>.md` (N = 0) or `<Name>.revised-vN.md` and writes its `.review.md`. Stage `spec-review`, attempt N+1.
  - `revise -Revision N` reads revision N-1 and its review, writes `<Name>.revised-vN.md`, then validates it. Stages `spec-revise` and `revised-validate`, attempt N.
  - RN-12: a FAIL verdict gives exit 1 `review_failed` (the stage is `succeeded` with verdict FAIL, no next round is planned). `revise` validates the reviser output: validator exit 1 or 3 is exit 1 `validation_failed`; another code or a throw is exit 2 `stage_failed`.
  - An existing output is `artifact_exists` (manifest written, stage `skipped` with `not reached: artifact_exists`); with `-Overwrite` that file alone moves to `runs\<id>\replaced\` (artifact role `replaced`).
- `status -RunId` prints `runId`, `workflow`, `recordedStatus`, `status` (derived: `abandoned` by `Get-HarnessRunStatus`), `exitCode`, stages, warnings, `error`, manifest path. Unknown run: `invalid_arguments`; unreadable or schema-invalid manifest: `manifest_invalid`.
- `list [-Last N]` prints runs newest first by `createdAtUtc` (fallback: folder creation time) with the derived status; an unreadable manifest is `unreadable`. Both accept `-Json` (one line; a failure is one `ERROR:` line, exit 2). Neither writes.

## 2. Interface for the next package (B6: artifact lock, concurrent runs)

- **Where to lock.** `review` and `revise` run through `Invoke-HarnessCliSingleRun` in `lib\cli.ps1`. Take the artifact mutex right after the first `Save-HarnessCliRun` (the manifest with the planned stages) and before the `artifact_exists` check, as for `specify` in `Invoke-HarnessCliSpecifyRun`. `artifact_in_use` follows the `artifact_exists` branch: `Stop-HarnessCliSpecifyRun -Run $Run -Category 'artifact_in_use' -Message ...`. RN-11: `review` and `revise` hold the lock; `status` and `list` never do.
- **What to lock on.** The name family (`<Name>` in `<target>\.ai-harness\specs`), the same key for `specify`, `review` and `revise`. The files each command touches: `review` one `.review.md`; `revise` one `.revised-vN.md`; `-Overwrite` also writes under `runs\<id>\replaced\`.
- **Warnings.** `concurrent_run_detected` goes into `$Run.Warnings` before the first `Save-HarnessCliRun` (the handlers build `$harnessSpecifyRun` with `Warnings = @($claim.Warnings)`).
- **Shared handler.** `Invoke-HarnessCliSingleCommand` repeats the claim/`try`/`finally`/protocol skeleton of `Invoke-HarnessCommandSpecify` (the variable is still named `$harnessSpecifyRun`: the workflow hook reads it by dynamic scope). A lock released in a `finally` fits in both.
- **Status and liveness.** `status` and `list` use `Get-HarnessRunStatus` only; a lock owner that dies is `abandoned` through the manifest `pid`, so B6 needs no new state for them.
- **Tests.** The mocks and helpers of `test-harness-review-status.ps1` (`Invoke-Cmd`, `New-Target`, the wait mock `cli-reviewer-wait.ps1` with an event file) can drive a second command while a first one waits. The planned `test-harness-concurrency.ps1` can start the waiting child as in the AC-315 case.
- **Workflow functions.** `Invoke-ReviewWorkflow` and `Invoke-ReviseWorkflow` take `-ContextFile` (passed only when bound); B7 adds it to the CLI handler call (`$workflowArguments`) and to the reviewer and reviser scripts.
